# R0.12 Preview — libmpv LGPL Hard-Gate Exclusion

**Work Order:** `R0.12-PREVIEW-BACKEND-BENCHMARK-001`  
**Date:** 2026-08-16  
**Status:** ACCEPTED — HARD-GATE-EXCLUDED-FOR-STAGE-A  
**Candidate family:** libmpv on Windows

## Decision scope

This is a **Stage-A Preview selection exclusion**, not a claim that libmpv is technically poor or permanently forbidden.

The Work Order required one of two outcomes before Preview ADR closure:

1. an auditable Windows libmpv candidate using the approved LGPL path; or
2. a documented hard-gate exclusion when a reproducible Windows LGPL build/distribution path imposes disproportionate product, deployment, licensing or maintenance risk.

The second outcome is accepted.

## Upstream facts

Audited upstream release:

- mpv `v0.41.0`;
- release commit `41f6a645068483470267271e1d09966ca3b9f413`;
- mpv is GPLv2-or-later by default;
- mpv supports an LGPLv2.1-or-later mode with `-Dgpl=false`;
- the official Windows compilation documentation supports shared `libmpv-2.dll` and explicitly warns that `-Dgpl=false` users must review corresponding subproject options;
- the normal upstream Windows CI configuration for this release is not an LGPL product candidate because its build script enables top-level GPL and FFmpeg GPL options.

Therefore an ordinary upstream Windows binary cannot be silently treated as the product's auditable LGPL libmpv dependency.

## Why the Windows LGPL path became a hard gate

The product selection priority for this Work Order is:

`deployability / compatibility / diagnosable degradation`
`>`
`stable external control / simple user operation`
`>`
`resource efficiency / acceleration`
`>`
`UI richness`

To retain the D3D11 path required for the Windows Preview candidate, mpv `v0.41.0` requires both shaderc and SPIRV-Cross in its D3D11 renderer configuration.

A reproducible LGPL-oriented candidate therefore requires project-owned control over at least:

- exact mpv revision and `gpl=false`;
- FFmpeg GPL/nonfree configuration;
- libass revision/license;
- libplacebo revision/license;
- shaderc revision/license;
- SPIRV-Cross revision/license;
- shaderc's fixed nested dependency closure, including glslang and SPIR-V tooling;
- Windows Clang/LLVM + Visual Studio SDK build environment;
- direct DLL dependency closure and redistribution notices;
- exact build options proving GPL/nonfree features were not silently enabled.

This is materially different from consuming an official Windows runtime whose provenance and redistribution surface are already prepared by the upstream project.

## Reproducibility investigation performed

A benchmark-only GitHub Actions build path was constructed from the upstream `v0.41.0` Windows/Clang route. It intentionally attempted to produce an auditable shared libmpv candidate rather than accepting a third-party binary.

The investigation found and classified multiple independent boundaries:

1. workflow YAML Windows-path quoting defect — harness failure;
2. GitHub `windows-latest` image drift from historical VS2022 assumptions to a newer Visual Studio image — environment assumption defect; fixed through `vswhere` discovery;
3. PowerShell empty-string parameter binding — harness failure;
4. historical upstream shaderc bootstrap following a moving checkout no longer accepted the old patch — upstream moving-dependency/build-route drift;
5. an added `prefer_static=true` constraint incorrectly forced Windows system library resolution — harness overconstraint; removed;
6. D3D11 configuration proved that shaderc **and** SPIRV-Cross are required for this mpv release;
7. shaderc was pinned to `v2024.1` and SPIRV-Cross to `vulkan-sdk-1.3.290.0` to remove moving-master ambiguity;
8. the most advanced accepted diagnostic run successfully completed Meson dependency discovery/setup and generated build targets for FFmpeg, shaderc/glslang/SPIRV tooling, libplacebo and the mpv shared library before a remaining PowerShell continuation defect stopped the benchmark harness.

The investigation therefore did **not** prove that libmpv itself is unbuildable. It proved that obtaining and maintaining the required **auditable LGPL Windows distribution candidate** is a bespoke dependency/build product in its own right.

That distinction is intentional: harness failures are not candidate failures.

## License-chain interpretation

ADR-008 requires the complete dependency license chain, not only the top-level repository license.

The investigation verified that the relevant upstream projects expose permissive/LGPL-compatible top-level licensing routes, but shaderc brings an additional fixed nested dependency closure that must still be reconciled at actual link/distribution level. For example, glslang's license bundle contains multiple permissive licenses and historical parser-license text with an exception; this cannot responsibly be reduced to a one-word top-level classification without auditing the actual linked/redistributed closure.

No claim is made here that the attempted candidate is GPL-contaminated. The accepted conclusion is narrower:

> Stage A would need to own and continuously maintain a non-trivial custom Windows build, pinning and license-notice process merely to keep libmpv eligible.

## Comparison with already-qualified candidates

GStreamer and libVLC already have:

- official Windows distribution channels;
- accepted private-runtime provenance in this Work Order;
- real windowed playback PASS;
- deterministic external API control PASS;
- real-phone HEVC playback PASS;
- explicit software decode fallback PASS on the tested Class-A host;
- LGPL-oriented engine/framework licensing suitable for an adapter architecture, subject to ordinary redistribution/notices review.

libmpv has not produced product-relevant evidence that justifies taking on a substantially larger custom build/license maintenance surface merely to enter the same Preview adapter competition.

## Hard-gate result

**libmpv is HARD-GATE-EXCLUDED from the Stage-A Preview backend decision.**

Reasons:

1. no upstream-provided Windows artifact was accepted as the required auditable LGPL libmpv candidate;
2. the product would need to maintain a custom Windows build and transitive license/notices closure;
3. D3D11 eligibility expands that closure through shader translation dependencies;
4. the resulting maintenance/deployment burden is disproportionate while two other candidate families already satisfy the product's actual Preview hard gates;
5. continuing to iterate the custom build would violate the benchmark STOP principle by turning player selection into an open-ended build-system project.

## Revisit condition

This exclusion may be reconsidered only if a concrete product need appears and at least one of the following materially changes:

- mpv provides an upstream auditable Windows LGPL libmpv distribution path with bounded dependency/notices evidence;
- the project adopts a maintained packaging system that already owns this dependency closure;
- GStreamer/libVLC later fail a real product requirement that libmpv uniquely solves.

Do not reopen libmpv merely to obtain a third green benchmark row.

## Cleanup rule

The experimental libmpv build workflow/harness is not production infrastructure and must not become an always-failing repository maintenance surface after this exclusion. Its useful conclusions are preserved in this validation record and the Preview ADR.
