## GStreamer 1.28.6 — Wave 1

Command path used the private GStreamer runtime and explicitly selected `d3d11videosink` for actual windowed playback.

Observed process-level measurement:

- wall time: approximately `13.683s`;
- first observed window handle: approximately `518 ms` after process start;
- CPU time: approximately `5.609s`;
- average machine CPU estimate: approximately `10.2%` on this 4-logical-processor host;
- max working set: approximately `139.7 MiB`.

Diagnostic evidence:

- Direct3D11 devices were created/enumerated during actual playback;
- D3D11 presentation window was created and later destroyed normally;
- the runtime reports unsupported VP8/VP9/AV1 decode capability for some enumerated D3D11 devices on this legacy host;
- one enumerated D3D11 device reported `0x80004002` / unsupported interface when queried for video-device capability;
- despite that, actual playback completed and the visible D3D11 presentation window was destroyed at normal end of playback.

Interpretation at Wave 1:

- actual D3D11 presentation path is active;
- hardware H.264 decoder registration was proven in Stage 1, but the Wave-1 excerpt alone did not prove beyond ambiguity that decodebin selected `d3d11h264dec`;
- the device-enumeration warning is retained as diagnosable degraded-environment evidence and is not hidden by removing Oray before the benchmark;
- the missing D3D11/DXGI debug libraries are developer debug-layer diagnostics, not a playback failure.

## Wave 2A — GStreamer actual playbin3 hardware path proof — PASS

After retiring two brittle manual `filesrc/qtdemux` proof pipelines and correcting a Windows PowerShell 5.1 native-stderr harness defect, the same deterministic fixture was run through the actual high-level GStreamer playback stack using:

- canonical `file:///` URI input;
- `playbin3` / `uridecodebin3` / `decodebin3`;
- `GST_PLUGIN_FEATURE_RANK=d3d11h264dec:MAX`;
- explicit `d3d11videosink`;
- `Start-Process` with separated stdout/stderr;
- `GST_DEBUG_DUMP_DOT_DIR` pipeline topology capture.

Observed:

- playback process exit code: `0`;
- five DOT graphs captured across NULL→READY→PAUSED→PLAYING→PAUSED→READY state changes;
- `GstD3D11H264Dec:d3d11h264dec0` present in the actual autoplugged `decodebin3` graph;
- `GstD3D11VideoSink:d3d11videosink0` present in the actual `playsink` graph;
- decoder context reports hardware device `Intel(R) HD Graphics 520`, vendor `8086`, device `1916`, `hardware=true`;
- H.264 constrained-baseline 1920x1080@30 input reaches `d3d11h264dec0`;
- decoder output is `video/x-raw(memory:D3D11Memory)`, NV12, 1920x1080@30;
- D3D11-memory NV12 remains present through the downstream playback graph into `d3d11videosink0`.

Interpretation:

- GStreamer hardware H.264 decode selection is now directly proven on this host through the actual playback stack, not merely through decoder registration;
- actual decode→presentation path is `playbin3 → decodebin3 → d3d11h264dec → D3D11Memory/NV12 → d3d11videosink`;
- the prior manual-pipeline failures remain benchmark harness defects and do not reduce candidate acceptance;
- the GStreamer hardware-path proof gate is closed and must not be reopened by further manual demux experiments.

The probe's PASS marker is emitted only after its internal control checks complete. Those checks include:

- start playback and wait for timeline position availability;
- pause and require bounded timeline drift;
- execute the same sequence of eight absolute randomized seeks while paused;
- require each seek to recover into the target tolerance before timeout;
- resume and require normal timeline advancement;
- stop and release the player cleanly.

Interpretation:

- both GStreamer GstPlay and libVLC 3 satisfy the deterministic non-GUI control hard gate on this Class-A restored-vendor-driver host and deterministic fixture;
- both are suitable in principle for a thin `PreviewBackend` adapter from a play/pause/absolute-seek/control perspective;
- no backend winner is declared from Wave 2B alone;
- the terminal summary did not expose the per-seek numeric stdout payload, so this durable record accepts the behavioral PASS but does **not** invent or rank mean/max seek-recovery proxy milliseconds;
- if a numeric seek-performance comparison becomes decision-critical, read the persisted local evidence files under `%LOCALAPPDATA%\\video-editing-agent-preview-benchmark\\wave2b-api-control` rather than reconstructing numbers from the PASS marker.

## Harness defects discovered and retired

1. The first Wave-2 manual `filesrc -> qtdemux -> ...` proof pipeline was structurally brittle and failed before a meaningful decoder result.
2. A second manually linked `qtdemux` attempt again failed at the source-start boundary despite the same fixture already succeeding through `gst-play-1.0`.
3. Windows PowerShell 5.1 treated GStreamer DEBUG messages written to native stderr as PowerShell errors under `$ErrorActionPreference = "Stop"`, prematurely aborting an otherwise valid playbin3 run.
4. A giant inline PowerShell 5.1 control harness used multiline boolean syntax that failed parser rules before either candidate executed.
5. The first file-based runner incorrectly assumed MinGW-style `libgstplay-1.0-0.dll` naming even though the prepared official GStreamer runtime is MSVC and exposes `gstplay-1.0-0.dll`.
6. The accepted runner uses small file-based `.ps1`/`.py` probes, MSVC-aware DLL discovery, `Start-Process`, separated stdout/stderr and child exit codes.
