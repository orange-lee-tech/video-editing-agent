# R0.12 Preview Wave 2 — Harness Correction

**Work Order:** `R0.12-PREVIEW-BACKEND-BENCHMARK-001`  
**Date:** 2026-08-16  
**Classification:** BENCHMARK_HARNESS_DEFECT; CANDIDATE RESULT UNCHANGED  

## Observed failures

The first Wave-2 explicit GStreamer proof command failed with:

- `Failed to start`
- `ERROR: pipeline doesn't want to preroll.`
- `Failed to set pipeline to PAUSED.`

The script therefore stopped before the API-level seek/scrub probes.

A second supplemental attempt explicitly naming `qtdemux`'s video pad also failed at the source-start boundary and reported the failure under:

`/GstPipeline:pipeline0/GstFileSrc:filesrc0`

with the same preroll failure pattern.

A third attempt correctly moved to the actual high-level playback stack (`playbin3`) with a canonical `file:///` URI, `d3d11h264dec` rank preference and D3D11 sink. The PowerShell wrapper stopped immediately after GStreamer wrote a normal DEBUG line to native stderr:

`DEBUG d3d11h264dec ... device support resolution 1920x1088`

No `playbin3 exit code = ...` line was reached. This is classified as a Windows PowerShell 5.1 wrapper defect, not a GStreamer playback failure: the wrapper used `$ErrorActionPreference = "Stop"` together with direct native invocation and PowerShell redirection, allowing stderr diagnostic output to be surfaced as an Error-stream record and terminate the wrapper before process exit evaluation.

## Interpretation

None of the three failures is accepted as a GStreamer backend failure.

Wave 1 already demonstrated successful real-window playback of the same deterministic fixture through the prepared private GStreamer runtime with a D3D11 video sink. The failing commands were benchmark-only proof wrappers introduced solely to gather extra decoder/control evidence.

The first manual pipeline was structurally brittle because MP4 demuxing exposes dynamic pads. GStreamer documentation recommends using `playbin3` / `uridecodebin3` for ordinary audio/video playback and describes `GST_PLUGIN_FEATURE_RANK` as the supported mechanism for enabling or preferring a hardware decoder. GStreamer also provides `GST_DEBUG_DUMP_DOT_DIR` specifically to inspect the internal topology created by all-in-one playback elements such as `playbin`.

The second failure occurred at `filesrc` start, before it could establish a meaningful result about H.264 decode or D3D11 presentation. Because `gst-play-1.0` already opened and played the same file successfully in Wave 1, this pointed back to benchmark command/path argument construction rather than candidate media capability.

The third attempt reached `d3d11h264dec` registration and then the PowerShell wrapper itself terminated on normal native stderr/debug output before an exit code could be collected. Microsoft PowerShell documentation notes that native commands commonly write informational text to stderr and that the handling of redirected native stderr changed in PowerShell 7.2; this host uses Windows PowerShell 5.1. Therefore direct `& native.exe` invocation with `$ErrorActionPreference = Stop` is not accepted for subsequent benchmark logging on this host.

## Corrective rule

- Preserve the accepted Wave-1 GStreamer playback result.
- Do not change drivers, disable Oray, reinstall runtimes, or downgrade GStreamer because of these harness failures.
- Retire the explicit `filesrc -> qtdemux -> ...` proof pipeline from the benchmark. Do not spend further cycles repairing it.
- Use the actual playback stack (`playbin3` / `GstPlay`) for subsequent evidence.
- Prefer `d3d11h264dec` through `GST_PLUGIN_FEATURE_RANK` and inspect the resulting playback graph/debug evidence instead of forcing a manual demux chain.
- On Windows PowerShell 5.1, run native benchmark processes with `Start-Process -RedirectStandardOutput/-RedirectStandardError -Wait -PassThru` and classify success from the process exit code plus explicit evidence markers. Do not let normal native stderr diagnostics become PowerShell terminating errors.
- Use API-level pause/seek/scrub behavior as the primary control-plane hard gate.
