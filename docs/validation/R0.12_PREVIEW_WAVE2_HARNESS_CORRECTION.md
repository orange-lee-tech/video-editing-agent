# R0.12 Preview Wave 2 — Harness Correction

**Work Order:** `R0.12-PREVIEW-BACKEND-BENCHMARK-001`  
**Date:** 2026-08-16  
**Classification:** BENCHMARK_HARNESS_DEFECT; CANDIDATE RESULT UNCHANGED  

## Observed failure

The first Wave-2 explicit GStreamer proof command failed with:

- `Failed to start`
- `ERROR: pipeline doesn't want to preroll.`
- `Failed to set pipeline to PAUSED.`

The script therefore stopped before the API-level seek/scrub probes.

## Interpretation

This failure is **not** accepted as a GStreamer backend failure.

Wave 1 had already demonstrated successful real-window playback through the prepared private GStreamer runtime and D3D11 presentation path. The failed Wave-2 command was an extra benchmark-only proof pipeline constructed as:

`filesrc -> qtdemux -> queue -> h264parse -> d3d11h264dec -> d3d11videosink`

For an MP4 containing both video and audio, `qtdemux` exposes dynamic stream pads. GStreamer documentation demonstrates naming the demuxer and explicitly linking stream pads such as `demux.video_0` / `demux.audio_0`, or using the playback/autoplugging stack (`decodebin` / `uridecodebin` / `playbin`) rather than treating `qtdemux` as a single static output.

Therefore the first Wave-2 explicit proof pipeline is classified as a **benchmark harness construction defect**.

## Corrective rule

- Do not discard the accepted Wave-1 GStreamer playback result.
- Do not change drivers, disable Oray, reinstall runtimes, or downgrade GStreamer because of this harness failure.
- Future GStreamer control evidence should use the actual playback stack (`GstPlay` / playbin-equivalent) and decoder-rank / diagnostic evidence rather than making a brittle manual demux chain a prerequisite.
- If an explicit MP4 video-only proof is still useful, link the named dynamic video pad explicitly, e.g. `qtdemux name=demux demux.video_0 ! ...`, and treat it as supplemental evidence only.
