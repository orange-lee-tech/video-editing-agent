## 3. Private-runtime contract

The production adapter does not assume arbitrary global GStreamer installation.

Initialization requires a selected private runtime root containing the required GStreamer/GstPlay DLL and plugin surfaces. It configures the process environment deliberately for the session:

- runtime `bin` is prepended to `PATH`;
- `GST_PLUGIN_SYSTEM_PATH_1_0` points to the selected private plugin directory;
- `GST_PLUGIN_PATH_1_0` is cleared for the bounded adapter session;
- `GST_REGISTRY_1_0` uses a controlled registry location;
- the previous environment is restored on release.

The adapter checks the expected `1.28.x` runtime family and records version/provenance in `PreviewStatus`.

Full ordinary-user install/repair UX remains outside this Work Order and belongs to the later Windows Environment Doctor boundary.

## 4. Exact playback semantics

The accepted playback surface is intentionally small:

```text
initialize
→ load local media
→ play / pause
→ absolute seek(MediaTime)
→ status / exact position
→ stop
→ release
```

Seek does not reinterpret timeline meaning. `MediaTime` is converted to nanoseconds only when the value is exactly representable; otherwise the request fails with a typed `INVALID_SEEK` diagnostic instead of silently rounding into a second timeline authority.

GStreamer playback state and bus messages are diagnostic/runtime truth only. Canonical EDL remains the exact executable timeline authority.

## 5. Software-video decode fallback semantics

`SOFTWARE_VIDEO` does not mean "disable all GPU use".

The accepted behavior is narrower:

1. enumerate registered GStreamer decoder factories;
2. retain only factories separately classified as both `Hardware` and `Video`;
3. temporarily set only those hardware video decoder factory ranks to `GST_RANK_NONE`;
4. leave presentation/conversion/sink/source factories alone;
5. restore every changed rank on release.

This preserves the legal route "CPU/software video decode + GPU presentation" where the runtime/platform supports it.

### First real-probe defect — explicitly rejected

The first production Windows run was:

- run `32029185354`;
- job `95385079915`.

Both playback modes executed, but the first dynamic implementation passed a combined `DECODER | HARDWARE | VIDEO` list type to `gst_element_factory_list_get_elements` and incorrectly treated the result as an intersection.

Real diagnostics exposed false positives including software decoders and non-decoder elements such as `avdec_h264`, `openh264dec`, converters, sinks and sources.

That run was **not accepted** even though the workflow playback steps were green.

The production implementation was repaired to:

- enumerate Decoder factories first;
- call `gst_element_factory_list_is_type(..., Hardware)` separately;
- call `gst_element_factory_list_is_type(..., Video)` separately;
- demote only factories passing both checks.

This is an example of the real Product/Engineering Probe correcting a false-positive implementation that deterministic fake APIs did not expose.

## 8. What PASS does not mean

This PASS does **not** mean:

- Preview may modify canonical EDL;
- Preview may become Renderer/final-export authority;
- every Windows GPU/driver combination has been validated;
- the hosted runner demonstrated physical hardware-decoder disablement;
- a global user-installed GStreamer runtime is accepted implicitly;
- full Environment Doctor/installer/repair UX is complete;
- real VFR coverage has been added;
- libVLC is silently bundled as an automatic fallback;
- libmpv Stage-A exclusion has been reopened;
- another backend-family benchmark is needed.

Known bounded risks remain:

- real VFR corpus coverage is still open;
- Class-B/C codec/device breadth remains future Product-Probe evidence;
- no-GPU/driver/presentation failures still need ordinary-user Environment Doctor diagnostics;
- frontend embedding/presentation integration remains a later product-facing boundary.
