# R0.3 Footage Understanding — Validation Record

Status: **IN PROGRESS — provider-neutral foundation validated**

## R0.3-A — analysis contract and deterministic sampling

Implemented and validated:

- reviewed `AnalysisProfile` values: `basic`, `semantic`, `speech`, `deep_visual`, `editorial`;
- revisioned derived `ShotAnalysis` tied to an exact `Shot` revision;
- `UnderstandingService` application port;
- deterministic midpoint-of-bin frame sampling;
- exact Shot revision traceability and unique increasing sample timestamps.

At commit `17fd613da281244cf3b050d84ea91ee3b16a7fed`, the main quality gate passed with
90 tests and 79 checked source files.

## R0.3-B — real frame extraction

Implemented `FramePlanExtractor` and the FFmpeg PNG backend without introducing a VLM provider.

The real Windows probe at commit `71e562a823c5276e1abb7706bad89928b4cd9f73` generated a two-second
320x180 video and sampled Shot revision `sht_sampling_probe@2` at deterministic positions:

```text
Shot frame sampling probe: PASS
shot_ref=sht_sampling_probe@2
timestamps_ms=[333, 1000, 1666]
frame_sizes_bytes=[29774, 25203, 25324]
dimensions=320x180
```

Both `ci/quality-gate-diagnostic` and `ci/shot-frame-sampling-windows` passed.

## R0.3-C — durable artifact and visual proposal boundary

Implemented:

- application-owned `ArtifactStore` port;
- SHA-256 content-addressed `LocalArtifactStore` implementation;
- deterministic persistence of extracted frame payloads;
- `VisualFrameReference` preserving ordinal and source timestamp;
- provider-neutral `VisualUnderstandingPort`;
- `VisualSemanticsProposal` as non-domain provider output;
- deterministic proposal normalization before Domain use.

The provider cannot create `ShotAnalysis`, and filesystem paths do not become artifact identity.
At commit `95001cb23e5ab7cfe9b0928c60364d4d7782f1b9`, the main quality gate passed with
99 tests and 85 checked source files.

## R0.3-D — UnderstandingService revision ownership

Implemented the provider-neutral visual UnderstandingService owner with explicit repository and media
resolution ports. Its data flow is:

`ShotRef -> ShotRepository -> AssetMediaResolver -> sampling -> real frame extractor -> ArtifactStore -> VisualUnderstandingPort -> VisualSemanticsProposal -> deterministic normalization -> ShotAnalysis revision -> ShotAnalysisRepository`

The visual implementation currently supports `semantic`, `deep_visual` and `editorial`. `speech` and
`basic` are deliberately not faked; unsupported profiles fail explicitly until their own capabilities
exist.

The real Windows ownership probe at commit `fe62e09c812a552d0fc7388a511a9b5c8ee0dfe8` used a real
two-second video, real FFmpeg PNG extraction and a real local ArtifactStore. Only the visual model was
a deterministic fake provider. Observed result:

```text
UnderstandingService ownership probe: PASS
shot_ref=sht_understanding_probe@3
analysis_revisions=[1, 2]
profiles=['semantic', 'editorial']
provider_frame_counts=[3, 5]
artifact_counts=[3, 5]
normalized_tags=('synthetic', 'test-pattern')
```

Both `ci/quality-gate-diagnostic` and `ci/understanding-owner-windows` passed.

This proves that provider output remains a Proposal while `UnderstandingService` retains authority to
create `ShotAnalysis@1` and `ShotAnalysis@2` against the exact same immutable Shot revision.

## Next boundary

Before choosing a concrete VLM SDK, the upstream footage-understanding implementation is reviewed for
prompt/schema/retry ideas only. Any provider adapter must stay behind `VisualUnderstandingPort`, read
image bytes through `ArtifactStore`, and return only `VisualSemanticsProposal`.

A real visual provider, persistent Shot/Analysis repositories, speech analysis and ShotIndex remain
separate implementation work. None is claimed complete by this validation record.
