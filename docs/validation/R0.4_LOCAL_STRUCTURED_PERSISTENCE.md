# R0.4 Local Structured Persistence — Validation Record

Status: **CLOSED — 2026-08-10**

## Objective

R0.4 closes the gap between the validated R0.3 footage-understanding ownership model and a durable
local application state. The requirement is not merely to serialize objects: exact revisioned `Asset`,
`Shot` and `ShotAnalysis` records must survive process restart while their existing Domain/Application
owners remain authoritative.

Binary frame payloads are intentionally outside this structured-record database and continue to use the
SHA-256 content-addressed `ArtifactStore` introduced in R0.3.

## R0.4-A — persistence decision

ADR-0001 selected Python 3.12's standard-library SQLite integration for the local-first v0.x baseline.
The decision freezes these initial constraints:

- SQLite schema version `1` via `PRAGMA user_version`;
- foreign keys enabled on every connection;
- exact revision primary keys;
- explicit transactions and rollback;
- deterministic, versioned record codecs;
- idempotent re-save of identical exact revisions;
- conflicting content for an existing exact revision fails loudly;
- no SQLAlchemy, server database, required WAL mode or migration framework yet;
- binary artifacts do not move into SQLite.

Decision commit:

`d51c384144c71279d7dd346c574f586a811f673e`

## R0.4-B — SQLite repositories and owner seams

Implemented:

- application-owned `AssetRepository` port;
- persistence extension for `ShotRepository` with transactional `save_many()`;
- `SqliteProjectDatabase` schema/bootstrap boundary;
- deterministic codecs for `Asset`, `Shot` and `ShotAnalysis`;
- `SqliteAssetRepository`;
- `SqliteShotRepository`;
- `SqliteShotAnalysisRepository`;
- exact Asset -> Shot and Shot -> ShotAnalysis foreign keys;
- row/payload identity integrity checks;
- exact-revision conflict detection;
- batch Shot rollback if any member of the batch fails.

Owner integration remains explicit:

- `AssetIngestService` creates the `Asset`, then optionally persists the committed record;
- `ShotCatalog` creates the complete authoritative Shot set, then persists it atomically;
- `UnderstandingService` continues to create `ShotAnalysis` revisions and call its repository;
- repository implementations never allocate IDs or semantic revisions.

Implementation commits:

- `76ebf42b1bdf932c439c6ed22e2be409bf1af913` — SQLite repositories and codecs;
- `ef845fc4b7e33d07b4169b8126c8e92d0af5c49b` — Asset/Shot owner persistence seams.

Automated regression coverage includes schema bootstrap/version rejection, restart round trips,
foreign-key enforcement, exact-revision idempotency, conflict rejection and transactional batch
rollback.

## R0.4-C — real two-process Windows persistence proof

A repository-backed local media resolver was added so an exact persisted Asset revision can recover a
local `file:` URI without exposing filesystem layout to `UnderstandingService`.

The dedicated Windows workflow intentionally runs two separate Python processes against the same SQLite
database and ArtifactStore.

### Process 1 — seed

The first process performs:

`real video -> ffprobe -> AssetIngestService -> SQLite Asset -> ShotCatalog -> SQLite Shot -> real FFmpeg PNG extraction -> ArtifactStore -> deterministic visual proposal -> UnderstandingService -> SQLite ShotAnalysis@1`

Observed output:

```text
SQLite persistence seed: PASS
schema_version=1
asset_ref=ast_sqlite_persistence_probe@1
shot_ref=sht_sqlite_persistence_probe@1
analysis_revision=1
artifact_count=3
```

The seed process then exits.

### Process 2 — resume

A new Python process opens the same database and independently reconstructs repository/resolver/service
objects. It must recover the exact Asset, Shot and prior analysis, resolve the original local media,
and continue the owner revision chain through `reanalyze()`.

Observed output:

```text
SQLite persistence resume: PASS
schema_version=1
asset_ref=ast_sqlite_persistence_probe@1
shot_ref=sht_sqlite_persistence_probe@1
analysis_revisions=[1, 2]
artifact_counts=[3, 5]
```

The proof therefore covers actual process-boundary recovery rather than only rebuilding repository
objects inside one interpreter.

## Boundaries preserved

R0.4 does **not** claim or introduce:

- storage ownership of Domain identity or revision creation;
- a concrete visual-model provider;
- speech understanding;
- ShotIndex/retrieval;
- multi-user or distributed database behavior;
- production backup/recovery tooling;
- concurrent multi-writer guarantees;
- required WAL mode;
- a schema migration framework;
- binary frame storage inside SQLite;
- renderer or end-user application completion.

## Closure

R0.4 is accepted as complete because the repository now has a minimal local structured persistence
backend whose revision integrity is tested, whose ownership boundaries match Architecture Contract
v0.1.2, and whose Asset -> Shot -> ShotAnalysis state has been proven to survive separate Windows
Python processes while real media and real extracted-frame artifacts remain usable.

The next phase must be selected from the current repository state rather than inferred from an older
plan. Any new provider, index or editing capability must build on this accepted persistent baseline.
