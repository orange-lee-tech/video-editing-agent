# R0.5 Shot Retrieval Foundation — Validation Record

Status: **CLOSED — 2026-08-10**

## Objective

R0.5 establishes `ShotIndex` as rebuildable retrieval infrastructure over authoritative `Shot` facts and
derived `ShotAnalysis` revisions. It must help later Resolver work find candidates without becoming a
Domain authority or a second source of truth.

This phase intentionally does not choose a vector database, embedding provider or concrete visual model.
Those can extend the retrieval implementation later without changing the application-facing contract.

## R0.5-A — provider-neutral ShotIndex contract

Added an application-owned retrieval port with:

- `ShotIndexSource` — exact `Shot` + exact `ShotAnalysis` pair;
- `ShotSearchConstraints` — retrieval prefilters for Asset revision, analysis profile and duration;
- `ShotCandidate` — derived candidate ref, analysis revision, retrieval score and evidence terms;
- `ShotIndex` — `upsert`, `rebuild`, `remove`, and `search` operations.

The contract explicitly treats constraints as retrieval prefilters only. Resolver remains responsible for
hard eligibility checks before any future `ResolutionDecision` is committed.

A zero-dependency `LexicalShotIndex` baseline was added with:

- deterministic Unicode normalization;
- Latin token retrieval;
- CJK character and bigram expansion for useful Chinese matching without a tokenizer dependency;
- weighted visual summary/tag/subject/action/environment/framing/camera-motion fields;
- speech transcript retrieval when speech facts exist;
- deterministic scores in `[0, 1]`;
- exact Shot revision identity;
- newer ShotAnalysis revisions replacing older derived index content;
- stale analysis regression rejection;
- deterministic tie ordering;
- rebuild semantics that replace the prior derived index state.

## R0.5-B — rebuild from R0.4 persistence

Added `MaintainShotIndex` in the Application layer rather than injecting the index directly into
`UnderstandingService`.

The use case supports:

- `refresh(shot_ref)` — load exact Shot and latest persisted analysis, then upsert the derived index;
- remove a stale candidate when the exact Shot currently has no analysis;
- `rebuild(shot_refs)` — reconstruct the complete derived index for an explicit exact-ref scope;
- report refs skipped because they have no analysis;
- reject duplicate exact Shot revisions in one rebuild request.

SQLite integration regression tests prove that:

1. authoritative Asset/Shot/ShotAnalysis records survive in R0.4 storage;
2. fresh repository objects can read them;
3. a new in-memory ShotIndex can be rebuilt from those persisted facts;
4. Shots without analysis are skipped rather than invented;
5. persisting `ShotAnalysis@2` and refreshing replaces `@1` retrieval content.

## Boundaries preserved

R0.5 does **not** claim or introduce:

- candidate eligibility authority;
- `ResolutionDecision` creation;
- source-window selection;
- vector-search or embedding quality claims;
- persistent derived index storage;
- a concrete VLM or embedding provider;
- ShotAnalysis mutation by the index;
- direct coupling between UnderstandingService and indexing;
- Director, Resolver, EDL or rendering completion.

## Closure

R0.5 is accepted as complete because the repository now has a provider-neutral retrieval contract, a
useful deterministic local implementation, and an Application-owned rebuild/refresh path from the R0.4
authoritative persistence baseline.

The index remains disposable and reproducible. Future vector or hybrid retrieval can be added behind the
same contract, while Resolver must still revalidate every candidate before editing decisions become
formal.

The next phase returns to the deliberately deferred R0.3 boundary: select and validate the first real
`VisualUnderstandingPort` provider adapter using current official provider contracts, without changing
UnderstandingService ownership.
